# A link's ingress drain is bounded by a compile-time budget, and a spent budget waits for the core's idle task, never for a clock

<!-- status: accepted -->

Status: **accepted** (2026-10-03, maintainer ruling; ships in v0.18.0). Applies [ADR-0081](0081-pre-sink-ingress-native-window-hold-or-named-drop-never-parked.md) §2 (hold ingress in the transport's native window) to a link that is already delivering, and keeps the standing no-timers rule ([`CLAUDE.md`](../../CLAUDE.md) §Design rules). The knob follows the compile-time-by-default rule of [ADR-0068](0068-build-configuration-is-plain-cpp-config-header.md).

## Context

`httpd_ws_link_t` reads its peers on the `esp_http_server` task (priority 5). The server's loop `select()`s on every session socket and calls the link's URI handler once per readable request, and the handler reads one WebSocket frame. While a peer keeps sending, the socket is readable again as soon as the handler returns, so `select()` never blocks. Together with the TCP/IP and Wi-Fi tasks that bring the bytes in, the httpd task keeps the core busy for as long as the peer keeps sending.

On a single-core ESP32 target the idle task then never runs. The task watchdog watches the idle task, so a peer that sends without pause for longer than the watchdog period resets the board. On an ESP32-C6 a burst of about 2,000 small writes over 15–16 s starved the idle task for 10–14 s (httpd 41 %, TCP/IP 30 %, Wi-Fi 19 % of the CPU) and the 15 s watchdog fired. Faster Wi-Fi only shortened the burst.

Two fixes were measured on silicon. Yielding for 2 ticks once the idle task had been starved for 100 ms did not help: the TCP/IP and Wi-Fi tasks and the priority-2 tasks filled each yield. Pausing the ingress for about 20 ms worked (the longest starvation fell to 0.89 s) because 20 ms is long enough for the peer's TCP window to close. But a pause measured in milliseconds is a timer and a clock read, which libtracer does not allow.

## Decision

**1. A drain has a budget of frames and bytes.** A **drain** is the run of frames a link's receive context consumes while its core never goes idle. When the drain has consumed `kRxDrainFrames` frames or `kRxDrainBytes` payload bytes, the link stops reading before the next frame's payload. Either budget ends the drain, and the frame that crosses the byte line is read whole.

**2. A spent budget waits for the core's idle task, or for the link's own egress work.** The link blocks the receive context on a semaphore that the core's idle hook gives. The idle task runs only when no other task on that core is ready, so the wait ends exactly when the core has had one idle moment, however long the higher-priority work takes. This is the event the watchdog is waiting for, and it needs no timer and no clock read. The idle hook is installed once per core per process, through `esp_register_freertos_idle_hook_for_cpu`. Each idle pass advances a per-core epoch with one store, and gives the semaphore only while a link is waiting.

The same semaphore is given by any task that has just posted a send for the link to the httpd task through `httpd_queue_work`. The httpd task is the one drain of its own control queue, so a receive context parked for idle would otherwise hold every queued send behind it for as long as the core stays busy. The parked task is that httpd task, and nothing of its own is mid-write (the handler has read a header and nothing since), so it **sends the posted items itself, from inside the wait**, and the wait goes on. The link counts the sends it has posted and not yet sent (`egress_pending_`); a parked drain that finds the count non-zero sends every slot marked as posted exactly as `tx_work` would, lowest post ticket first so a session's frames keep their post order, and leaves the slot busy for the server loop's copy of the item, which finds it already sent and only releases the slot. A refused enqueue that races the park is resolved by the item's state word: exactly one party releases the slot, and a frame the park sent is a delivery, not a drop.

Egress therefore wakes the park and ingress waits for idle. No frame is read for an egress wake and the budget is not reset by one, so a peer that can make the link post a send per inbound frame buys no ingress with it. Such a peer exists: a write from a peer over another link or task to a vertex the flooding peer subscribes to is one `queue_send` per write, and an application that answers requests from its own task posts one per reply. (The flooding peer alone cannot: a reply or a push provoked by its own frame is serviced in-call on the httpd task and never touches the queue.) Returning from the handler to let the server loop run the item is not available: IDF consumes the frame's first header byte in `httpd_req_new` before the URI handler runs, so a handler that returns without the payload desynchronises the stream. Closes (`close_work`) are not run from the park; a close posted by another task waits for idle as every control item did before. The wake covers the link's own sends only; a second link sharing an adopted server is woken by idle alone.

**3. Back-pressure is TCP's.** While the receive context waits, the frame's payload and everything behind it stay in the socket. The lwIP receive window fills, the peer's TCP stack stops sending, and the TCP/IP and Wi-Fi tasks go quiet. That quiet is what lets the idle task run. No frame is dropped and no buffer is added to the library ([ADR-0081](0081-pre-sink-ingress-native-window-hold-or-named-drop-never-parked.md) §1–§2).

*Erratum (2026-11-24, [#2891](https://github.com/avatarsd-llc/libtracer/issues/2891)):* "no frame is dropped" holds at and above lwIP only. With ESP-IDF's default zero-copy receive, the segments a park leaves in lwIP keep the shared Wi-Fi driver receive buffers, and under a flood the driver drops frames below lwIP, which the peer recovers by TCP retransmission. [Backpressure and sizing §3.1 rule 4](../reference/22-backpressure-and-sizing.md) gives the measured effect and the `CONFIG_LWIP_L2_TO_L3_COPY` setting that avoids it.

**4. A core that idles on its own resets the drain.** Each frame reads the core's idle epoch. If the epoch has moved since the previous frame, a new drain starts at zero. A link whose peers do not saturate the core never waits, so the budget costs nothing on a node that is not flooded.

**5. The budget is a compile-time trait.** `tr::graph::default_config_t::kRxDrainFrames` (default 32) and `kRxDrainBytes` (default 32,768) are part of the build's one `config_t`, with `tr::net` spellings. The ESP-IDF component binds them from `CONFIG_LIBTRACER_WS_SERVER_RX_DRAIN_FRAMES` and `CONFIG_LIBTRACER_WS_SERVER_RX_DRAIN_BYTES`. `0` turns a budget off; with both off the gate compiles to nothing and no hook is installed. The ESP-IDF defaults are 32 and 32,768 only when the task watchdog watches the idle task of every core httpd may run on, and `0` otherwise (see Consequences: a non-zero budget requires a core that idles). The receiver pays: the cost lands on the node being flooded, and only while it is.

**7. A drain's replies must not wait on an ACK the drain itself is withholding.** The receive context is also the task that writes the in-call replies, and lwIP couples the two sides of a connection through the unread ingress. While the socket's recv mbox is full (`CONFIG_LWIP_TCP_RECVMBOX_SIZE`, 6 on the board) lwIP keeps the next segment as *refused data* and, until it is accepted, drops every further data-bearing segment from that peer before `tcp_process`, with the ACK numbers it carries (`lwip/src/core/tcp_in.c`, the `refused_data` test in `tcp_input`; `lwip/src/api/api_msg.c`, `recv_tcp`'s `sys_mbox_trypost`). A peer with data to send piggybacks its ACKs on that data, so the board's reply segments stay unacknowledged until the board reads. Under `TCP_NODELAY` a reply is two segments (header, payload), and a drain of 32 small replies queues 64 against lwIP's `TCP_SND_QUEUELEN` of 16; the ninth reply's write waits for an ACK only the waiting task can release, spends the socket's send bound, and fails: one reply refused (`tx_send_failed`), or a header on the wire with its payload lost (the #951 cut-off), and three in a row condemn a healthy session (no longer since [#2921](https://github.com/avatarsd-llc/libtracer/issues/2921): see the erratum at the end). This is what the ESP32-C6 run showed at budget 32 (4 of 30 bursts), and not at budget 8, where a drain is exactly 16 segments.

Two compile-time rules, both from the board's own lwIP configuration: (a) once a drain has read `TCP_SND_QUEUELEN / (2 × write legs)` frames back to back (4 at IDF's defaults), the session being drained is switched from `TCP_NODELAY` to Nagle, so the rest of the drain's replies coalesce into one or two segments. Nagle holds until the peer's next light drain, one that ends by idle before reaching that count, and `TCP_NODELAY` comes back with it. An interactive peer leaves the core idle between requests and never reaches it, so its replies keep the no-delay path; only a peer that floods pays, with replies batched by its own ACK clock. (b) A drain also ends when the in-call reply bytes it wrote reach `TCP_SND_BUF / 4` (1440 B at the default 5760), so the replies of the two drains that can be outstanding at once stay under half the send buffer. The bound covers in-call replies only. Pushes posted by other tasks and sent from inside the park (§2) are outside it: up to one pool depth of them (4 slots) can go out while the peer's ACKs are withheld (superseded by the 2026-10-12 amendment below), and four pushes of 1.5 KiB or more exceed `TCP_SND_BUF`, which ends in a counted `tx_send_failed` or a condemned session. A single in-call reply larger than `TCP_SND_BUF` has the same caveat; that one predates this ADR. No timer, no clock, no buffer: Nagle is TCP's, and both numbers are the build's.

**6. The wait is counted.** `httpd_ws_link_t::stats().rx_drain_waits` counts the times a drain ended on its budget. It is not a drop counter: a rising count means the TCP window is pacing a peer that sends faster than the node can serve.

## Why these defaults

The bound this fix gives is: the idle task is kept out for at most one budget of frames plus the higher-priority work that follows it. At the ~7.3 ms of board time per small request measured on the ESP32-C6, 32 frames is about 0.23 s (32 × 7.3 ms = 0.234 s). That is under a quarter of the shortest task watchdog IDF allows (1 s) and about a twentieth of its default (5 s), so the default is safe for any watchdog setting without being tuned per board.

The cost of a wait is the time until the core idles. When the flood is the only load, that is the time the TCP/IP and Wi-Fi tasks need to settle once the window has closed. That cost is paid once per 32 frames rather than once per frame, and the silicon run will measure it (below). A smaller budget tightens the bound and pays the wait more often. A larger one does the opposite, and at about 130 frames it would use half the 1 s minimum watchdog.

The byte default is the link's own frame cap (`kMaxFrameBytes`, 32 KiB), so one maximum-size frame is one drain. It is also about six default lwIP receive windows (5,760 B). Frames bound a flood of small writes, where the per-request overhead dominates. Bytes bound a flood of large frames, where the copy and decode dominate.

## Consequences

- **No timer, no clock.** The fix adds an idle hook, one static binary semaphore per core, and four small members per link (the drain epoch, its frame and byte counts, and the wait counter). It adds no thread and reads no time.
- **The whole httpd task waits, not just one session.** Other sessions on the same server, and closes posted by other tasks, are delayed by the same wait. The link's own queued sends are not: a posted send is sent from inside the park (Decision §2), in post order, so a push from a producer task reaches the wire without the core idling first and without the ingress moving. A reply serviced in-call never waits at all, since it is written before the next frame can park. **The bound: one park serves at most one pool depth of egress** (superseded by the 2026-10-12 amendment below). A slot the park sent stays busy until the server loop's copy of the item runs, and the loop does not run while the task is parked, so once every pool slot holds a sent item the next post finds no slot and is the counted pool miss (`tx_pool_misses`, `enqueue_drops`) it always was. The pool depth was the link's outstanding-send bound before this ADR and still is; a producer that must push more than that between two idle moments sizes `tx_slot_capacity` for it. The wait lasts only until the core idles, which is short once the flood is held back by TCP.
- **A flooding session's replies are batched; an interactive session's are not.** Decision §7 switches a session to Nagle only after a drain has read the flood threshold of frames without the core idling, and holds it until the peer's next light drain, one that ends by idle before reaching the threshold. A peer that flooded once and then only receives never produces that drain, so it keeps paying one delayed ACK per push burst until it sends lightly again or reconnects. On such a session a reply may wait for the peer's ACK of the previous coalesced segment before it leaves (the peer's delayed-ACK time, tens of ms), which is the latency the flooder pays for the correctness of its own stream. A lone request from a peer that leaves the core idle never sees it. Both thresholds are read from the board's `lwipopts.h`; the host test binds IDF's defaults.
- **A socket write that fails is now counted link-wide.** `stats().tx_send_failed` (also in `drop_stats().dropped_tx`) counts frames `httpd_ws_send_frame_async` refused, in-call or queued. Before, that loss was a WARN line and a per-session streak only, so a listener reading counters could see replies go missing and count no drop.
- **A spent budget waits for every lower-priority task on the core (priority inversion).** The idle task runs only once every other task on its core has blocked. So after one budget of back-to-back frames, the httpd task (priority 5) yields not just to the TCP/IP and Wi-Fi tasks but to every lower-priority ready task on its core, until all of them block. Before this fix httpd preempted them. A priority-2 task in the middle of 500 ms of work now holds the next frame back for up to those 500 ms. Under sustained load, the link's read rate is therefore bounded by the longest run of lower-priority work on its core. That is inherent in "wait for idle" and acceptable for a watchdog fix, but it is the latency an embedder will notice: it applies only once a budget is spent, and never to a link that leaves its core idle now and then.
- **A non-zero budget requires a core that idles.** If a task below httpd's priority never blocks on the httpd task's core, the idle task never runs. A drained link then waits for good: every session on the server stops, queued sends stop, and `httpd_stop()` and the link's destructor block behind the parked handler. With the task watchdog watching that idle task, the board was already being reset, so the budget changes nothing. But IDF lets an application turn that check off (`CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0=n`) precisely because it runs such a task, and there a link that worked before would stop after 32 frames over the life of the process. So the ESP-IDF options default to `0` (no pacing) unless the task watchdog watches the idle task of every core httpd may run on (`ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0`, plus `_CPU1` on a dual-core build). The component's CMake warns when an explicit non-zero budget is combined with the CPU0 check off. A build that turned the check off must leave both budgets at 0. The protection lives in the build configuration, so the host test cannot express it; the host test does show that a parked link stays parked until the idle hooks run.
- **A full hook table leaves that core unpaced.** IDF holds eight idle hooks per core. If registration fails, the link logs it once ("ingress unpaced") and does not pace on that core, because waiting for a hook that never runs would hang the receive context (`httpd_ws_drain_budget_unhooked` covers this). `stats().rx_drain_waits` then reads 0, which is indistinguishable from a link that never saturated its core. The log line is the only signal.
- **Dual-core targets: the budget is approximate for an unpinned httpd task.** The gate is per core, and a waiting link waits for the idle task of the core it is running on. `HTTPD_DEFAULT_CONFIG` leaves the httpd task unpinned, so it may migrate between frames. A drain records the core it started on. When the task finds itself on another core, it starts a new drain there rather than compare epochs across cores. A migrating task can therefore read more than one budget between idle moments of any single core. It never hangs, because it always waits on the gate of the core it is on. On dual-core targets the watchdog pressure is far lower, and pinning the httpd task (`httpd_config_t::core_id`) makes the budget exact.
- **Host links are unchanged.** Hosted transports read from their own threads under a preemptive OS and do not read the trait.

## On-silicon validation

The host test (`httpd_ws_drain_budget_test`) shows the counting: a sustained ingress parks after exactly one budget, holds the next payload unread, and resumes only when the idle hooks run; a send queued from another task while it is parked goes out from inside the park, and a flood of such sends buys the ingress nothing. The silicon run must show the rest. On an ESP32-C6 (single core) with the default budget and the advisory's reproducer (bursts of about 2,000 small writes over 15–16 s, task watchdog at 5 s and at 15 s):

1. **The watchdog no longer fires.** No task-watchdog reset over at least 10 consecutive bursts.
2. **The longest idle-task starvation per burst.** Measure it with the same instrument as the original report. Expect well under 1 s, compared with 10.3–13.9 s before the fix.
3. **Throughput cost.** Requests per second over the burst, with the default budget and with both budgets set to 0 (the pre-fix behaviour, run with the watchdog disabled or longer than the burst). Report the ratio. For comparison, the 20 ms pause cost about 21 % (102/s).
4. **`stats().rx_drain_waits`** at the end of a burst, to confirm the budget is what paced it (about burst frames / 32).
5. **Sensitivity.** Repeat 2 and 3 with `CONFIG_LIBTRACER_WS_SERVER_RX_DRAIN_FRAMES` set to 8 and 128 to find where the starvation bound and the throughput cost cross.
6. **No regression on a quiet link.** On an interactive session (the SPA), `rx_drain_waits` stays at 0.

## Amendment (2026-10-12): the TX pool is gone; egress is one latest-wins slot per peer

*(Ruled 2026-10-11, [#2095](https://github.com/avatarsd-llc/libtracer/issues/2095).)* The two pool statements above, §Why these defaults (b)'s "up to one pool depth of them (4 slots)" and §Consequences' "one park serves at most one pool depth of egress" with its `tx_slot_capacity` advice, are **superseded**. `httpd_ws_link_t` no longer has a link-wide TX pool, and `tx_slot_capacity` no longer exists. Each peer holds one slot: a reference to the frame on the wire and one to the newest frame waiting, both pointing at a refcounted block that each send gathers once for every destination peer. A newer frame replaces the waiting one, and the replacement is counted. The park still sends posted egress in post order (Decision §2). What it can send while the peer's ACKs are withheld is now bounded per peer, at two frames, rather than by a pool depth. The flush writes without waiting, so a full socket keeps its frame instead of failing the post. That frame resumes on the link's own events: the flush re-posts itself while a held write still moves bytes, and the next post, an inbound frame or the app's `flush_held()` also resumes it. A peer whose socket takes no byte across `kTxStallStrikes` consecutive replacements is struck. No timer and no clock read were added. §Why these defaults (a) and (b), the drain budget and the in-call byte bound, are unchanged. The body above stays as the record.

*Erratum (2026-11-25, [#2908](https://github.com/avatarsd-llc/libtracer/issues/2908)):* no peer is struck for refused frames any more. `kTxStallStrikes` and its count are deleted; a session holds at most one block of the large class (`kTxLargePerPeer`), a further large frame for it is a counted refusal, and a peer that stopped reading is closed by the application's liveness check (`sweep`).

*Erratum (2026-10-17, [#2195](https://github.com/avatarsd-llc/libtracer/issues/2195)):* the slot is now a per-peer queue, one frame on the wire and up to `kTxWaitDepth` (8) waiting, in which only a newer SAMPLE of the same path replaces a waiting frame; so the park's per-peer bound is 9 frames, not two, and a full queue is a counted refusal that never strikes the peer.

## Alternatives considered

- **A time-bounded pause (about 20 ms).** It worked on silicon, but it is a timer and a clock read. It would also pick the length of the pause in the library, when the right length depends on the board's TCP/IP and Wi-Fi timing.
- **Yield for a few ticks once the idle task has been starved for a while.** Measured on silicon and it failed: higher-priority tasks fill the yield, and detecting the starvation needs a clock.
- **An app-driven pacing seam** (the application tells the link when to resume). It reads no clock, but every embedder would have to drive it, and a node that forgot would either never resume or never pause. The idle task already marks the event the watchdog needs.
- **Lower the httpd task's priority while it drains.** That depends on round-robin time slicing at the idle priority, which is a tick-driven timer in all but name, and it changes the priority of a task the link may not own (the adopted-server constructor).
- **Close or drop a peer that sends too fast.** A rate limit needs a clock, and dropping data is a worse answer than letting TCP hold it when TCP can.
- **Exclude the socket from httpd's `select()` and resume it later.** IDF offers that only through its async-request API, and the resume would have to be posted from the idle hook through the control socket, which can block. The idle hook must not block.

## Amendment (2026-11-20): one write per frame, no Nagle switch, and the drain is counted per session

*([#2891](https://github.com/avatarsd-llc/libtracer/issues/2891).)* Under continuous load from several sessions on one link, a quiet session's READ latency rose 8–12×. Two parts of the original decision caused it, and this amendment replaces both.

**§7(a), the Nagle switch, is withdrawn.** The drain counters were per link, and the core never idled while other sessions kept sending, so the count stayed past the flood threshold. Every frame from a different socket then moved Nagle to that socket, quiet sessions included. Under Nagle a reply's payload write waited for a delayed ACK behind its header write. The switch existed only because a reply was two segments: `httpd_ws_send_frame_async` writes the header and the payload as two calls. The link now writes every frame of its own as **one `sendmsg`** over the header it encodes and the payload in place. That means no copy and no buffer, and lwIP queues every part before it sends. A reply below the MSS is one segment. The segment bound of §7 is kept without Nagle: in-call replies are charged per session, and a session waits once its replies reach `TCP_SND_QUEUELEN / 2` replies (8 at IDF's defaults) or `TCP_SND_BUF / 4` bytes (1440). Both of those limits are a connection's own in lwIP. `kIdfWsWriteLegs` stays only as the send-bound divisor of §Consequences, because IDF still writes its own PONG and CLOSE echo in two calls through the same override.

**§1–§4: the park is still needed, but it is charged per session.** The watchdog reason (§Context) does not depend on Nagle or on the write shape. A peer that never stops sending still keeps the httpd, TCP/IP and Wi-Fi tasks busy, so the park on the idle gate stays, with the same wait, the same egress-from-the-park rule (§2) and the same TCP back-pressure (§3). What changes is who waits. Each session keeps a one-word tally: the low half of the idle epoch of the drain it belongs to, its frame units and its reply units. A frame waits only when one of three things holds:

- **its own session** has read its share of the budget, meaning the budget U divided among the sessions that have read in this drain;
- its own replies have reached the bound above;
- the whole drain has read 2U units.

No session is charged for another session's frames: a quiet session reads a frame or two per drain and is not made to wait for the floods around it, and a flooding session waits once it has had its share.

**The bound.**
- Under fair interleaving, the shares end a drain at about U.
- Sessions that join one after another each take the share they joined with. N of them read U·H_N (H_N = 1 + 1/2 + … + 1/N, about 2.6U at seven), so the link-wide ceiling stops them at 2U.
- A drain therefore reads at most min(U·H_N, 2U) units plus one frame per session.
- At the defaults (32 frames, 16 sockets, about 7.3 ms per small request) that is 80 frames, about 0.58 s. That is still inside the 1 s minimum task watchdog the defaults were chosen for (§Why these defaults), with less margin than one budget had.

**Units.** The frame and byte budgets are folded into one count:
- with both budgets set, a frame costs one unit plus one per `kRxDrainBytes / kRxDrainFrames` bytes of payload, so a drain ends no later than either budget alone would;
- with the byte budget alone, a frame costs its payload in 32nds of the budget, rounded up, and at least one unit, an empty frame too;
- `CONFIG_LIBTRACER_WS_SERVER_RX_DRAIN_FRAMES` is limited to 254, the ceiling of a one-byte count.

**The reply bound is checked when the session reads.** In-call replies are charged to their destination session, which joins the current drain first. The bound stops that session only at its own next frame. A session that only receives is never parked by it, and its replies still count against lwIP's queue as §7 describes.

*Amendment (2026-11-27, [#2916](https://github.com/avatarsd-llc/libtracer/issues/2916)): reply units.* A reply was charged one unit plus one per 180 B, against 8 units, so the round-up parked a session a reply early (a 360–479 B reply cost 3 of 8). A reply now costs the more of one segment's share and its bytes' share, in one byte: 6 B units, 30 per segment, 240 per drain at IDF's defaults. Its bytes round down. A drain therefore writes a session the byte half, plus the one reply that crossed it, plus under one unit per earlier reply: the bound is checked at the session's next read and a reply is charged after it is written, so the crossing reply always goes out, as it did before (1916 B for 479 B replies, 2048 B for 1 KiB ones, at the defaults). A 200 B reply now parks at the segment half (8), a 360–479 B reply at the fourth, and a 480 B or larger reply where its bytes reach 1440 B. **The byte half stays at a quarter of `TCP_SND_BUF` per drain,** although raising it would let mid-size replies reach the segment half: the headroom also carries this session's own pushes and fan-out frames, which the bound does not count, including payloads above 1 KiB. An in-call reply that finds the send buffer full waits the send bound with the httpd task held for every session, is dropped when nothing went out, or closes the session when part of it did (a desynchronised stream). An application that needs more mid-size replies per drain raises the knee through lwIP's send buffer (`CONFIG_LWIP_TCP_SND_BUF_DEFAULT`), which raises both halves together.

What remains shared is inherent: while the httpd task is parked, no session is read, so a quiet session's frame that arrives during a park waits for that park. That wait is the time until the core idles, which is short once TCP holds the flood back. It is not a share of other sessions' frames.

Per-link state removed: the drain's frame, byte and reply counters, its core and the Nagle socket. Added: one 4-byte tally per session, which fits existing padding and has no bytes when the build does not pace, plus a per-link drain tag, session count and unit count. The session count only overcounts (a session that leaves mid-drain stays counted), which only makes the other sessions' waits come earlier. No timer, no clock read and no buffer were added. A session's first frame, the one that claims it, has no tally yet and is not paced. A task that migrated between cores reads another core's epoch, which almost never matches a tally's tag, and it starts a new drain. A tag that matches by chance causes one early wait, never a hang. The on-silicon procedure of §On-silicon validation is extended in the PR that lands this: the control session's READ p95 with three flooding sessions, before and after, plus the original flood test.

*Erratum (2026-11-27, [#2921](https://github.com/avatarsd-llc/libtracer/issues/2921)): a reply that times out is a drop, never a strike.* No count of failed sends closes a session any more. A hard socket error condemns it at once. An in-call reply that waits out the send bound with nothing written is a counted drop (`tx_send_failed`) and marks the session stalled; while it is stalled, its replies are written without waiting, so a stopped peer costs the httpd task one send bound and then nothing, however many replies a drain writes to it (up to the 8 of the amendment above). A reply the socket takes whole ends the stall; one it takes part of is finished within one bound, and a failure there is the #951 truncation close. A stopped peer is closed by the application's liveness check (`sweep`), which counts a stalled session as owing bytes, so a slow peer is never closed for timeouts alone. The send-bound derivation of §Consequences keeps its divisor of 3, now named `kSendBoundsPerPeer`: what a stopped peer can still cost per stall (the reply that found the socket full, the finish of a later part-taken reply) plus the margin the bound has carried since #840. The default stays 208 ms at four peers and a 5 s watchdog, and `peers × 3 × kIdfWsWriteLegs × bound` still fits one watchdog window.
